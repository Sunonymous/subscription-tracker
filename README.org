* Project Overview
This is an extremely simple subscription viewer and manager. You may enter data describing your personal financial subscriptions and view them all in one place. All data stays local and may be imported/exported to other devices at will. This tool should also work to provide a concrete record for your regular recurring expenses if the need of sharing it arises.

* UI Implementation Plan
The interface is being built incrementally, card-by-card, rather than all at
once. Each phase below is checked off once it actually lands in the code
sections further down, so this list stays a true reflection of what exists,
not just what was intended.

- [X] Phase 0 --- Retro documentation pass: short Org prose next to every existing code block explaining the /why/, not just the code.
- [X] Phase A --- Read-only subscription list: render
  =::subs/subscription-list= as abbreviated cards. Validates the data flow end-to-end before any interactivity is added.
- [X] Phase B --- Expand/collapse per card (local component state), showing full field detail.
- [X] Phase C --- Edit-in-place: an "Edit" toggle in the expanded card swaps to the same form used for creation, dispatching =::events/update-subscription=.
- [X] Phase D --- Create: an inline "+ Add subscription" form at the top of the list, dispatching =::events/add-subscription=. (Built ahead of Phase C: with no data at all, there was nothing to verify Phase B against, and this form is what Phase C will reuse for editing anyway.)
- [X] Phase E --- Delete: a control plus confirm step, dispatching =::events/remove-subscription=.
- [X] Phase F --- Accounts: mirror B--E for accounts, including delete confirmation copy that reflects the =::events/remove-account= unlink-cascade.
- [X] Phase G --- Category autocomplete and color assignment: a derived sub over =::db/categories= keys feeding a =<datalist>= on the subscription form, plus a way to set/change a category's =:color=.
- [X] Phase H --- Derived stats bar: a =subscription-tracker.util= namespace for cost normalization, plus a sub for total monthly/yearly spend and active count.
- [X] Phase I --- Filtering & sorting: a =:ui= app-db slice (sort key/direction, filters) plus controls; cancelled subscriptions sorted to the bottom and visually dimmed by default.
- [X] Phase J --- Import/export: download =:subscriptions=/=:accounts= as a file; re-validate through =::db/db= spec before merging an import back in.
- [X] Phase K --- Correctness/density pass from real usage: a fixed-term =:end-date= that's excluded from active-cost totals once passed; cost-sort normalized to a common period; a compact =$cost/freq= summary display with symbolic status; a cleaner import file-picker control.

** Known Follow-ups
Smaller items deliberately deferred rather than tackled mid-phase, to be
picked up once we're focused on styling specifically rather than on wiring
up behavior:

- [X] Style invalid form inputs (e.g. a required field left blank, or one

  before submission, not just enforced by it --- likely a CSS rule on

** Stylesheet
Colors live as CSS custom properties on =:root=, redefined once under
=@media (prefers-color-scheme: dark)=, rather than being written directly
into each rule --- every component then reads =var(--surface)=/
=var(--text)=/etc. instead of a hardcoded hex value, so the whole app
retheme consistently and light/dark stay in exactly one place each. Dark
mode follows the OS setting automatically (=color-scheme: light dark= on
=:root= also tells native form controls, like the color/date pickers, to
match) --- there's no toggle, no =:ui= state, and nothing to persist,
since the OS already knows the answer and the app has no reason to
second-guess it. Both palettes are deliberately muted rather than pure
white-on-black or black-on-white --- the complaint that prompted this pass
was a stark white background being hard on the eyes at night, and a pure
black background with pure white text has the same problem in reverse
(maximum contrast is exactly what's uncomfortable in a dark room); =--bg=/
=--text= stay a soft off-white/near-black pair in light mode and a dark
slate/soft-white pair in dark mode instead.

Cards, forms, and the stats bar use a =var(--surface)= background plus a
soft =var(--shadow)= for elevation instead of the =1px solid= borders they
used before --- a shadow implies "this sits above the page" the way a
border alone doesn't, and it's one less hardcoded color to carry between
themes (the shadow's opacity already does the right thing in both). A few
borders remain on purpose: =var(--border)= still underlines section
dividers (=.subscription-details=, =.data-panel=) and outlines form
controls, where a line genuinely separating two things reads better than
implying one floats above the other. =.entity-form--nested= additionally
clears its own background/shadow now, so an edit-in-place form doesn't
paint a second surface layer on top of the card it's already inside.
=input=/=select=/=textarea= and =button= each get one shared base rule
instead of being restyled per section (=.entity-form=, =.filter-controls=,
=.file-input-trigger= all used to repeat the same =padding=/=font:
inherit=) --- now there's one definition of what a text field or a button
looks like, and every place that needs one just gets it. =:focus-visible=
gets a visible =var(--focus)= outline app-wide, since relying on each
browser's own default focus ring would mean it's whatever color that
browser happens to pick against a background it knows nothing about.
=input:invalid=/=select:invalid= also pick up a =var(--danger)= border,
closing out the "Known Follow-ups" item from the UI roadmap --- plain
=:invalid= rather than =:user-invalid= (which Chrome and Safari don't
support) at the cost of a required-but-not-yet-touched field showing red
before the user has had a chance to fill it in, which is a minor,
accepted quirk rather than something worth tracking real "has this field
been touched" state in app-db just to avoid.

The two =default-*= maps are shapes/templates, not valid instances --- most
fields are =nil= placeholders meant to be =merge=d over when creating a real
entity (see =::events/add-subscription=/=::events/add-account=), not values
that satisfy the spec below on their own.

=:billing-day= is a plain integer, 1--31, rather than a full anchor date.
An earlier version stored a full ISO date so the next charge could in
principle be derived for any cadence uniformly, but nothing in the app
actually computes next-occurrence dates yet, and in practice what a user
wants to see and enter is "which day of the month it bills," not a specific
calendar date that happens to recur. This does mean day 31 doesn't exist in
every month --- deliberately not solved here; if/when real date-math lands
(e.g. a "next charge" calculation), it can decide how to clamp/roll that
case then, with real requirements in view instead of a guess now.

"Which day" doesn't mean the same thing for every =:frequency=, though:
=:monthly=/=:quarterly= recur on a day-of-month alone (any given month
works), =:weekly= recurs on a day-of-week (there is no "day 31" of a
week), and =:custom= isn't anchored to a calendar position at all --- it's
fully described by =:custom-interval-days=. Rather than force one field to
mean several different things, there are three optional fields:
=:billing-day= (1--31, for every month-based cadence) and
=:billing-weekday= (a day-of-week keyword, for =:weekly=) are mutually
exclusive as before; =:billing-month= (1--12) is additionally required
alongside =:billing-day= specifically for =:yearly=, since "bills on the
15th" genuinely doesn't say which month for something that happens once a
year --- unlike monthly/quarterly, where every recurrence lands in a
different month anyway, so day-of-month alone is already unambiguous. All
four fields are =s/nilable= --- every subscription always has all four
*keys* present (via the =default-subscription= merge), just with the
irrelevant ones' values left =nil= --- and =billing-info-valid?= below
enforces that the *relevant* ones are actually filled in for a given
=:frequency=, so this stays a real constraint rather than fields that are
technically optional and easy to forget. (An earlier version let =:custom=
through with no interval at all, on the theory that
=:custom-interval-days= alone already described it; in practice that just
meant it was possible to add a "custom" subscription that describes
nothing, with no feedback until =check-and-throw= rejected it against the
spec on save. Requiring it here up front is both a more accurate
constraint and a better UX --- see the =views.cljs= notes for the matching
=:required= attribute on that input. =:billing-month= went through the
same reasoning from the start, having been added once the gap was
noticed, rather than shipped first and tightened later like
=:custom-interval-days= was.)

=:status= exists so a subscription can become =:cancelled= without being
deleted --- the point is to keep spending history intact rather than lose
it, per the app's original "track and view" goal.

=:end-date= is for a fixed-term subscription that simply won't renew ---
mirroring =:start-date= (same =s/nilable string?= shape, same
=<input type="date">= origin) rather than introducing a different
representation for "when" just because this one marks an end instead of a
beginning. It's deliberately *not* folded into =:status=: whether a term
has ended is a fact about a date, independent of whether anyone remembered
to go flip the subscription to =:cancelled= once it did, and the two can
disagree (a term can end before =:status= catches up). =subs.cljs='s
=::active-subscriptions= and =views.cljs='s cancelled-styling both check
=util/past-end-date?= in addition to =:status= for exactly that reason ---
see their notes for how a subscription can display and sort like
=:cancelled= while its stored =:status= still honestly says =:active=.

The spec below uses unqualified keys (=s/keys :req-un=/=:opt-un=) because the
app's maps use plain keywords (=:id=, =:name=, ...) rather than namespaced
ones (=:subscription/id=) --- no translation is needed between the maps as
stored and the maps as validated. There is deliberately no foreign-key check
tying =:account-id= to a real entry in =:accounts=; see the notes next to
=events.cljs= for how =::remove-account= keeps that reference from dangling
instead.

=:color= lives on a *category*, not on the subscription. Asking for a color
per subscription would mean choosing one for every single entry; keying it
by category instead means related subscriptions (e.g. everything tagged
"streaming") share a color automatically, and it's chosen once. Categories
stay freeform strings on the subscription itself (no separate id, no
add/remove events) --- =:categories= is just a lookup map from category name
to its metadata, populated lazily as categories get used (see
=events.cljs='s =register-category=), not a managed collection with its own
lifecycle.

Phase I adds a =:ui= slice to =default-db= for the subscription list's
filter/sort controls (search text, status/category filters, sort key and
direction). It's real app-db state --- both the controls bar and the list
renderer need to read it --- but it's presentation of existing data, not
data itself, so it deliberately has no spec entry (=s/keys= on =::db=
ignores unrecognized keys, so this needs no change there) and =->local-store=
in =events.cljs= already only persists =[:subscriptions :accounts
:categories]=, so =:ui= is excluded from localStorage for free. That also
means it resets to these defaults on every page load, which is the right
behavior for view state (nobody expects their search box to still have
text in it from last visit).

Phase J adds =:import-error= to the same =:ui= slice, for the same reason:
whether the last import attempt failed (and why) is shared between the
event that does the validating and the panel that displays the result, so
it belongs in app-db rather than a local atom --- and like the rest of
=:ui=, it's fine to reset to =nil= on reload rather than persist, since a
stale error from a previous session has no use.

(ns subscription-tracker.db
  (:require [cljs.spec.alpha :as s]))

(def default-account
  "Shape of a single account entity: where a subscription's money comes from."
  {:id nil
   :name ""
   :last-digits ""
   :created-at nil
   :updated-at nil})

(def default-subscription
  "Shape of a single subscription entity. See README.org schema notes."
  {:id nil
   :name ""
   :cost 0
   :frequency :monthly            ;; #{:weekly :monthly :quarterly :yearly :custom}
   :custom-interval-days nil
   :billing-day nil               ;; 1-31; monthly/quarterly/yearly
   :billing-month nil             ;; 1-12; yearly only (day alone is ambiguous)
   :billing-weekday nil           ;; day-of-week keyword; weekly only
   :status :active                ;; #{:active :paused :cancelled}
   :account-id nil                ;; references an entry in :accounts
   :start-date nil
   :end-date nil                  ;; fixed-term subscriptions only; see util/past-end-date?
   :category nil                  ;; freeform, lowercased on save; see :categories
   :auto-renew? true
   :url nil
   :notes nil
   :created-at nil
   :updated-at nil})

(def default-db
  {:subscriptions {}              ;; map of id -> subscription entity
   :accounts      {}              ;; map of id -> account entity
   :categories    {}              ;; map of category name -> {:color ...}
   :ui            {:sort-by :name          ;; #{:name :cost :status}
                    :sort-dir :asc         ;; #{:asc :desc}
                    :status-filter nil     ;; nil (all) or a ::status
                    :category-filter nil   ;; nil (all) or a category name
                    :search ""             ;; substring match against :name
                    :import-error nil}})   ;; set by ::events/import-data on failure

;; -- Spec ------------------------------------------------------------------
;; Fields shared between entities

(s/def ::id string?)
(s/def ::name string?)
(s/def ::notes (s/nilable string?))
(s/def ::created-at (s/nilable string?))
(s/def ::updated-at (s/nilable string?))

;; Account Spec

(s/def ::last-digits string?)

(s/def ::account
  (s/keys :req-un [::id ::name ::last-digits]
          :opt-un [::created-at ::updated-at]))

(s/def ::accounts (s/map-of ::id ::account))

;; Subscription Spec

(s/def ::cost number?)
(s/def ::frequency #{:weekly :monthly :quarterly :yearly :custom})

Persistence uses =pr-str=/=cljs.reader/read-string= (edn) rather than JSON.
Edn round-trips ClojureScript data --- keywords, keyword values like
=:monthly= / =:active=, =nil= --- losslessly; JSON would need a translation
layer (stringifying/parsing keywords, deciding on a null convention) for no
real benefit, since nothing outside this app needs to read the stored value.
=cljs.reader/read-string= is used instead of raw =js/eval= specifically
because it is a /data/ reader --- it cannot execute code, so a corrupted or
tampered =localStorage= entry can fail to parse but never do anything worse.

=check-spec-interceptor= is placed /before/ =->local-store= in
=mutating-interceptors=. Interceptor after-phase functions run in reverse
list order, so that ordering actually means =->local-store='s =:after= runs
first, saving to =localStorage= before the spec check's =:after= gets a
chance to throw. This mirrors the standard re-frame todo-mvc reference
implementation's ordering; a spec violation still throws and surfaces
immediately either way (the bad write to =app-db= already happened by the
time either interceptor runs), so this is flagged rather than "fixed" ---
reordering would diverge from the well-known community pattern for a benefit
that is mostly theoretical at this app's scale.

=::remove-account= cascades --- it clears =:account-id= on any subscription
pointing at the deleted account --- while =::remove-subscription= does not
touch =:accounts=, because the dependency only runs one direction: a
subscription optionally /references/ an account, but an account has no
reference back, so deleting a subscription can't orphan anything. This was a
deliberate UX choice: auto-clearing the reference (with a confirmation
prompt in the UI, once built) beats forcing the user to manually unlink
every subscription first, since an account is incidental context for a
subscription, not something the subscription structurally depends on.

=normalize-category= lower-cases =:category= on the way into =app-db=
(applied in both =::add-subscription= and =::update-subscription=, so it's
enforced regardless of which UI surface submits the data, present or
future) specifically to stop "Streaming" and "streaming" from becoming two
separate categories by accident; the view layer is responsible for
presenting it capitalized. =register-category= then ensures =:categories=
gets an entry (defaulting to no color) for whatever category a subscription
just used, if it doesn't have one already --- this is what keeps
=:categories= populated from ordinary use, with no dedicated "manage
categories" UI required for the map to stay useful. =->local-store= now
persists =:categories= alongside =:subscriptions=/=:accounts=, since it's
real user data (assigned colors) that needs to survive a reload just like
the rest.

=::set-category-color= (Phase G) is deliberately its own event rather than
something folded into =::update-subscription=: a category's color is
shared by every subscription tagged with it, not a property of the one
subscription you happen to be editing when you pick it, so it takes effect
immediately rather than waiting on that subscription's form to be saved.
It uses =update-in=, not =register-category='s =update ... (or % ...)=,
because setting a color is an explicit overwrite --- there's no existing
value to preserve the way =register-category= preserves an
already-assigned color when a subscription merely reuses a category.

Phase I's five events (search text, status filter, category filter, sort
key, sort direction) all write to the =:ui= slice added to =default-db=
above, and deliberately skip =mutating-interceptors=: they're not
"significant changes" to validate or persist in the sense the rest of this
section means it --- =:ui= has no spec entry and =->local-store= never
looks at it anyway, so running either interceptor on every keystroke of a
search box would just be wasted work. =::toggle-sort-dir= flips between
=:asc=/=:desc= rather than taking an explicit value, since the only thing a
direction control needs to do is reverse whatever it currently is; changing
the sort key (=::set-sort-by=) deliberately leaves direction alone instead
of resetting it to =:asc=, so re-sorting by a different column preserves
"ascending/descending" as the user last set it rather than surprising them
back to a default.

=::import-data= (Phase J) takes the raw text of a user-selected file ---
=views.cljs= does nothing but read the file and hand over its contents,
since parsing and validating are decisions about /data/, not about file
I/O, and belong here with the rest of that logic. =reader/read-string= is
the same edn reader =localstorage.cljs= already uses, for the same
reasons (lossless keyword/nil round-tripping, can't execute code the way
=js/eval= could) --- an exported file is just the =->local-store= payload
written to disk instead of localStorage, so reusing the format means
export and import are inverses of the same serialization rather than two
separate formats to keep in sync. Unlike every event above, =::import-data=
deliberately does /not/ let a bad spec just throw: that's exactly the
uncaught =check-and-throw= crash already seen once this project from stale
data, and a hand-crafted or corrupted import file is a far more likely way
to hit it than schema drift ever was. Instead it =merge=s the imported
=:subscriptions=/=:accounts=/=:categories= onto the current ones (imported
entries win on a shared id/category name, new ones are simply added,
matching the plan's "merging an import back in" rather than replacing
outright) into a candidate db, checks /that candidate/ against =::db/db=
itself, and only commits it if valid --- otherwise =db= passes through
unchanged and =:ui='s =:import-error= is set to =s/explain-str='s
explanation instead. =mutating-interceptors= still runs on top of this (so
a successful import is checked and persisted exactly like any other
change), but by the time it does, =check-and-throw= is validating a db
this event already confirmed is valid, or one it never touched --- so that
interceptor can never actually throw here; the explicit check above is
what turns "crash" into "see why, try again."

Phase H needs to turn a subscription's cost + frequency into a comparable
number across the whole collection (for the stats bar's monthly/yearly
totals), which is pure arithmetic with no re-frame or app-db involvement
--- a separate, dependency-free namespace rather than tucking it into
=subs.cljs= keeps that math testable and reusable on its own, and keeps
=subs.cljs= itself about reading =app-db=, not computing with it. The
functions take the whole subscription map rather than loose
=cost=/=frequency=/=custom-interval-days= args so call sites stay simple
(=(util/annual-cost sub)=) instead of having to destructure and thread
three fields through by hand. =annual-occurrences= treats a malformed
=:custom= subscription (no positive =:custom-interval-days=) as
contributing =0= rather than letting a stray =NaN= poison the whole sum
--- the form doesn't currently mark that field as required, so this is a
real case, not a hypothetical one.

=past-end-date?= is the app's first bit of logic that compares stored data
against /today/ rather than just against other fields --- added so a
fixed-term subscription whose =:end-date= has passed stops contributing to
the active-cost totals even if nobody remembered to flip its =:status= to
=:cancelled=. =:start-date=/=:end-date= are both whatever an
=<input type="date">= produces: a plain =yyyy-mm-dd= string, zero-padded,
with no timezone component. That format happens to order identically
whether compared lexicographically or chronologically, which is what lets
this stay string comparison --- =compare=, not =<=, since =<= is numeric-only
in Clojure(Script) and will warn/fail on strings (an early draft of this
reached for =<= directly and tripped exactly that warning). =today-str=
builds the same =yyyy-mm-dd= shape from =js/Date='s *local* getters
(=.getFullYear=/=.getMonth=/=.getDate=) rather than reaching for
=.toISOString= (which is UTC) ---
comparing a local-date input against a UTC "today" could disagree about
what day it is for several hours around midnight in any timezone that
isn't UTC itself. This sidesteps needing any real date-parsing library for
a single day-granularity comparison.

(ns subscription-tracker.util)

(defn annual-occurrences
  "How many times per year a subscription bills."
  [{:keys [frequency custom-interval-days]}]
  (case frequency
    :weekly 52
    :monthly 12
    :quarterly 4
    :yearly 1
    :custom (if (and custom-interval-days (pos? custom-interval-days))
              (/ 365 custom-interval-days)
              0)))

(defn annual-cost [subscription]
  (* (:cost subscription) (annual-occurrences subscription)))

(defn monthly-cost [subscription]
  (/ (annual-cost subscription) 12))

(defn- pad2 [n]
  (if (< n 10) (str "0" n) (str n)))

(defn- today-str []
  (let [d (js/Date.)]
    (str (.getFullYear d) "-" (pad2 (inc (.getMonth d))) "-" (pad2 (.getDate d)))))

(defn past-end-date?
  "True when `subscription`'s :end-date is set and has already passed."
  [{:keys [end-date]}]
  (and end-date (neg? (compare end-date (today-str)))))

Subscriptions are split into two layers, the standard re-frame convention:
"layer 2" subs (=::subscriptions=, =::accounts=) are thin extractors that
pull the raw map straight out of =app-db= and do nothing else, while
"layer 3" subs (=::subscription-list=, =::subscription=, =::account-list=,
=::account=) build on those via =:<-= input signals rather than reading
=db= directly. Keeping the extractors separate means every derived sub ---
including future ones, e.g. filtered/sorted views in Phase I --- shares the
same memoized =::subscriptions=/=::accounts= reaction instead of each
re-deriving its own path into =app-db=.

Phase F adds =::subscriptions-for-account=, parameterized by an account id
like =::subscription=/=::account= already are. It exists specifically so
the account-delete confirmation (=views.cljs=) can say how many
subscriptions reference the account before you commit to deleting it,
mirroring in the UI the unlink behavior =::events/remove-account= already
performs in =app-db=.

Phase G adds a =::categories= layer-2 extractor and two layer-3 subs on
top of it: =::category-names= (sorted keys, for the subscription form's
autocomplete) and =::category-color=, parameterized by category name like
=::account=/=::subscription= are by id. =::category-color= is deliberately
its own sub rather than exposing the whole =category-info= map, since the
view only ever needs the color, and keeping the parameter a plain name
string (not an id) matches how =:categories= is actually keyed.

Phase H adds the stats bar's three subs, all built on a new
=::active-subscriptions= (status =:active= only --- a cancelled or paused
subscription isn't currently costing anything, so it shouldn't count
toward "what am I spending"). It also excludes anything
=util/past-end-date?= flags, on the same logic: a fixed-term subscription
past its own end date isn't actually costing anything either, whatever its
stored =:status= still says --- see the =db.cljs= note on =:end-date= for
why that's checked separately rather than requiring =:status= to be kept
in sync by hand. =::total-monthly-cost=/=::total-yearly-cost=
delegate the actual per-subscription math to =subscription-tracker.util=
and just =reduce= it over the active list; keeping that arithmetic out of
=subs.cljs= (see the =util.cljs= note) means these subs are purely about
"which subscriptions, summed how," not about the cost formula itself.
Deliberately unrelated to Phase I below: the stats bar always summarizes
*every* active subscription, not whatever the list's current filters
happen to be showing, so it stays on =::subscription-list=/
=::active-subscriptions= rather than the new filtered/sorted sub.

Phase I adds a =::ui= layer-2 extractor over the new =:ui= app-db slice,
and one layer-3 sub per field (=::sort-by=, =::sort-dir=,
=::status-filter=, =::category-filter=, =::search=) so the controls bar
can subscribe to just the one value each control actually renders, rather
than the whole =:ui= map and a re-render on every unrelated field change.
=::filtered-subscriptions= is where search/filter/sort actually happen,
built on six input signals (the raw list plus all five =:ui= fields) so it
recomputes only when something it actually depends on changes. Filtering
and sorting are deliberately one sub rather than two separate subs chained
together --- an intermediate "filtered, not yet sorted" value has no use
anywhere else, so splitting it would just add a reaction with no purpose.
Cancelled subscriptions --- and, since =util/past-end-date?= was added,
anything past its own =:end-date= too, even if still nominally =:active=
--- sort to the bottom *unconditionally*, ahead of whatever
=::sort-by=/=::sort-dir= the user picked, by comparing on
=[cancelled-or-expired? sort-value]= pairs: =compare= on the boolean half
already decides the ordering for any mismatched pair, so the chosen sort
only ever breaks ties among subscriptions that agree on
cancelled-or-expired-or-not. Search
matches purely on a lower-cased substring of =:name=; the status and
category filters are plain equality checks (including =nil= meaning "no
filter," so the default --- nothing chosen yet --- naturally shows
everything). =sort-value= resolves the actual field to compare on, with a
fallback to name so an unrecognized =:sort-by= degrades instead of
exploding. Sorting =:cost= uses =util/monthly-cost=, not the subscription's
raw stored =:cost=, since the raw number is only comparable to another
subscription's raw number when they share the same billing frequency ---
a $35/yr subscription is cheaper overall than a $20/mo one despite the
smaller raw number, and sorting on the unnormalized value would rank them
backwards.

Phase J adds =::export-data=, built on the same three layer-2 extractors
as =::import-data='s merge target (=::subscriptions=/=::accounts=/
=::categories=) so there's exactly one definition of "the data" shared by
export, persistence, and spec validation --- it returns precisely the
shape =::events/import-data= expects to read back, and the shape
=->local-store= already persists. =::import-error=, by contrast, is a
plain extractor straight off =::ui= (not its own layer-2/3 split) since
there's nothing to derive --- it is the field.

 :<- [::sort-by]
 :<- [::sort-dir]
 (fn [[subscriptions search status-filter category-filter sort-by sort-dir] _]
   (let [search (str/lower-case (or search ""))
         matches? (fn [{sub-name :name :keys [status category]}]
                    (and (or (str/blank? search) (str/includes? (str/lower-case sub-name) search))
                         (or (nil? status-filter) (= status status-filter))
                         (or (nil? category-filter) (= category category-filter))))
         inactive? (fn [sub] (or (= (:status sub) :cancelled) (util/past-end-date? sub)))
         rank (fn [sub] [(inactive? sub) (sort-value sort-by sub)])
         comparator (fn [a b]
                      (let [[a-cancelled? a-val] (rank a)
                            [b-cancelled? b-val] (rank b)]
                        (cond
                          (not= a-cancelled? b-cancelled?) (compare a-cancelled? b-cancelled?)
                          (= sort-dir :desc) (compare b-val a-val)
                          :else (compare a-val b-val))))]
     (->> subscriptions
          (filter matches?)
          (sort comparator)))))

   {:subscriptions subscriptions :accounts accounts :categories categories}))

(def ^:private month-names
  ["January" "February" "March" "April" "May" "June"

(defn- frequency-shorthand
  "Compact unit for the combined cost/frequency display, e.g. \"mo\" in
   \"$9.99/mo\"."
  [{:keys [frequency custom-interval-days]}]
  (case frequency
    :weekly "wk"
    :monthly "mo"
    :quarterly "3mo"
    :yearly "yr"
    :custom (str custom-interval-days "d")))

(defn- format-cost-frequency
  "\"$cost/shorthand\", plus a parenthetical normalized monthly estimate
   for anything that doesn't already bill monthly --- see the note above
   this component for why."
  [{:keys [cost frequency] :as subscription}]
  (let [base (str "$" (.toFixed cost 2) "/" (frequency-shorthand subscription))]
    (if (= frequency :monthly)
      base
      (str base " (~$" (.toFixed (util/monthly-cost subscription) 2) "/mo)"))))

(defn- status-symbol
  "Compact glyph for :status, with a trailing \"?\" when an :active
   subscription is past its own :end-date --- see the note above this
   component."
  [{:keys [status] :as subscription}]
  (case status
    :active (if (util/past-end-date? subscription) "↻?" "↻")
    :paused "⏸"
    :cancelled "⊘"))

  "Hover text for `status-symbol`, standing in for a header/legend row."
  [{:keys [status] :as subscription}]

    :active (if (util/past-end-date? subscription)

   :category "" :account-id ""
   :auto-renew? true :url "" :notes ""})

(defn- blank->nil [s]
  (when (seq s) s))

(defn- form->subscription
  "Coerces raw string form state into the shape ::events/add-subscription expects."
  [{:keys [name cost frequency custom-interval-days billing-day billing-month
           billing-weekday start-date end-date category account-id auto-renew? url notes]}]
  {:name name
   :cost (js/parseFloat cost)
   :frequency frequency
   :custom-interval-days (when (= frequency :custom) (js/parseInt custom-interval-days))
   :billing-day (when (contains? #{:monthly :quarterly :yearly} frequency)
                  (js/parseInt billing-day))
   :billing-month (when (= frequency :yearly) (js/parseInt billing-month))
   :billing-weekday (when (and (= frequency :weekly) (seq billing-weekday))
                       (keyword billing-weekday))
   :start-date (blank->nil start-date)
   :end-date (blank->nil end-date)
   :category (blank->nil category)
   :account-id (blank->nil account-id)
   :auto-renew? auto-renew?
   :url (blank->nil url)
   :notes (blank->nil notes)})

(defn- subscription->form
  "Inverse of form->subscription: seeds form state from an existing subscription."
  [{sub-name :name :keys [cost frequency custom-interval-days billing-day billing-month
                           billing-weekday start-date end-date category account-id auto-renew? url notes]}]
  {:name sub-name
   :cost (str cost)
   :frequency frequency
   :custom-interval-days (if custom-interval-days (str custom-interval-days) "")
   :billing-day (if billing-day (str billing-day) "")
   :billing-month (if billing-month (str billing-month) "")
   :billing-weekday (if billing-weekday (name billing-weekday) "")
   :start-date (or start-date "")
   :end-date (or end-date "")
   :category (or category "")
   :account-id (or account-id "")
   :auto-renew? auto-renew?
   :url (or url "")
   :notes (or notes "")})

(defn- form-field
  "Wraps `input` in a label, adding a modified-field accent when `k`'s
   current value differs from the form's initial value (edit mode only).
   When `accent-color` is given, the accent border uses it directly
   (so it matches the item's category instead of clashing with it);
   otherwise it falls back to the generic `field-modified` color."
  ([modified? k label-text input] (form-field modified? k label-text input nil))
  ([modified? k label-text input accent-color]
   (if (and (modified? k) accent-color)
     [:label {:class "field-modified-accent" :style {:border-left-color accent-color}}
      label-text input]
     [:label {:class (when (modified? k) "field-modified")} label-text input])))

(defn subscription-form

  [{:keys [initial on-success on-cancel]}]

        initial-form (when initial (subscription->form initial))

    (fn [{:keys [initial on-success on-cancel]}]
      (let [current @form
            dirty? (and initial-form (not= current initial-form))
            modified? (fn [k] (and initial-form (not= (get current k) (get initial-form k))))
            {form-name :name :keys [cost frequency custom-interval-days
                                     billing-day billing-month billing-weekday start-date end-date
                                     category account-id auto-renew? url notes]} current
            accounts @(re-frame/subscribe [::subs/account-list])
            category-names @(re-frame/subscribe [::subs/category-names])
            category-key (when (seq category) (str/lower-case category))
            category-color (when category-key @(re-frame/subscribe [::subs/category-color category-key]))]
        [:form.entity-form
         {:class (when initial "entity-form--nested")
          :on-submit (fn [e]
                       (.preventDefault e)
                       (if-let [id (:id initial)]
                         (re-frame/dispatch [::events/update-subscription id (form->subscription @form)])
                         (re-frame/dispatch [::events/add-subscription (form->subscription @form)]))
                       (when-not initial (reset! form empty-subscription-form))
                       (when on-success (on-success)))}
         [form-field modified? :name "Name"
          [:input {:type "text" :required true
                   :value form-name
                   :on-change #(swap! form assoc :name (.. % -target -value))}]
          category-color]
         [form-field modified? :cost "Cost"
          [:input {:type "number" :step "0.01" :required true
                   :value cost
                   :on-change #(swap! form assoc :cost (.. % -target -value))}]
          category-color]
         [form-field modified? :frequency "Frequency"
          [:select {:value (name frequency)
                    :on-change #(swap! form assoc :frequency (keyword (.. % -target -value)))}
           (doall
            (for [f [:weekly :monthly :quarterly :yearly :custom]]
              ^{:key f} [:option {:value (name f)} (name f)]))]
          category-color]
         (when (= frequency :custom)
           [form-field modified? :custom-interval-days "Interval (days)"
            [:input {:type "number" :min "1" :step "1" :required true
                     :value custom-interval-days
                     :on-change #(swap! form assoc :custom-interval-days (.. % -target -value))}]
            category-color])
         (when (= frequency :yearly)
           [form-field modified? :billing-month "Billing Month"
            [:select {:value billing-month :required true
                      :on-change #(swap! form assoc :billing-month (.. % -target -value))}
             [:option {:value ""} "Select a month"]
             (doall
              (for [[i month-name] (map-indexed vector month-names)]
                ^{:key i} [:option {:value (str (inc i))} month-name]))]
            category-color])
         (when (contains? #{:monthly :quarterly :yearly} frequency)
           [form-field modified? :billing-day "Billing Day (1-31)"
            [:input {:type "number" :min "1" :max "31" :step "1" :required true
                     :value billing-day
                     :on-change #(swap! form assoc :billing-day (.. % -target -value))}]
            category-color])
         (when (= frequency :weekly)
           [form-field modified? :billing-weekday "Billing Weekday"
            [:select {:value billing-weekday :required true
                      :on-change #(swap! form assoc :billing-weekday (.. % -target -value))}
             [:option {:value ""} "Select a day"]
             (doall
              (for [d [:sunday :monday :tuesday :wednesday :thursday :friday :saturday]]
                ^{:key d} [:option {:value (name d)} (str/capitalize (name d))]))]
            category-color])
         [form-field modified? :start-date "Start Date"
          [:input {:type "date"
                   :value start-date
                   :on-change #(swap! form assoc :start-date (.. % -target -value))}]
          category-color]
         [form-field modified? :end-date "End Date"
          [:input {:type "date"
                   :value end-date
                   :on-change #(swap! form assoc :end-date (.. % -target -value))}]
          category-color]
         [form-field modified? :category "Category"
          [:input {:type "text" :list datalist-id
                   :value category
                   :on-change #(swap! form assoc :category (.. % -target -value))}]
          category-color]
         [:datalist {:id datalist-id}
          (doall
           (for [c category-names]
             ^{:key c} [:option {:value (str/capitalize c)}]))]
         (when category-key
           [:label "Category Color"
            [:input {:type "color"
                     :value (or category-color "#cccccc")
                     :on-change #(re-frame/dispatch
                                  [::events/set-category-color category-key (.. % -target -value)])}]])
         [form-field modified? :account-id "Account"
          [:select {:value account-id
                    :on-change #(swap! form assoc :account-id (.. % -target -value))}

            (for [{:keys [id name last-digits]} accounts]

(defn- export-data!
  [data]
  (let [blob (js/Blob. #js [(pr-str data)] #js {:type "application/edn"})
        url (js/URL.createObjectURL blob)
        filename (str "subscription-tracker-export-"
                      (.slice (.toISOString (js/Date.)) 0 10) ".edn")
        a (js/document.createElement "a")]
    (set! (.-href a) url)
    (set! (.-download a) filename)
    (.click a)
    (js/URL.revokeObjectURL url)))

(defn- import-file!
  [file]
  (let [reader (js/FileReader.)]
    (set! (.-onload reader)
          (fn [e]
            (re-frame/dispatch [::events/import-data (.. e -target -result)])))
    (.readAsText reader file)))
